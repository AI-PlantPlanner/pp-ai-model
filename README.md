# pp-ai-model
AI 식물플래너 진단/추천 모델

## 개요
- 식물 100종 데이터 + 사용자 환경값(광량/온도/습도/실내·실외) 비교 → 식물별 적합도 점수(0~100점) 산출
- 입력은 게임에서 넘어온 **기간 누적 환경값**(3개월 등). 단일 시점 스냅샷보다 누적이 타당하다는 게임팀 판단
- 실사용자 데이터 없는 단계라 룰 기반 채점 로직을 "정답"으로 삼아 ML 모델이 근사하도록 학습(teacher-student 방식)

## 필요 스택
- Python 3.11, 가상환경 `.venv` 사용
- pandas, numpy: 데이터 처리
- scikit-learn: 모델 학습(GradientBoostingRegressor)
- joblib: 모델 저장/로드
- skl2onnx, onnx, onnxruntime: ONNX 변환 및 검증

## 환경 설정
```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## 파이프라인
- 1단계 `data_normalization.py`: 원본 엑셀 텍스트 범위값 → min/max 숫자 컬럼 정규화
- 2단계 `teacher_scoring.py`: 룰 기반 채점, 사용자 환경 vs 식물 적정범위 비교 → 0~100점
- 3단계 `synthetic_data.py`: 환경값 대량 샘플링 + 2단계 룰로 자동 라벨링 → 학습 데이터 생성
  - 환경 샘플링은 `env_profiles.py`가 만든 LLM 환경 프로파일을 쓰고, 없으면 균등 샘플링으로 폴백
- 4단계 `train_model.py`: "환경+식물 → 점수" 예측 회귀모델 학습 (v0 베이스라인 / v2 프로덕션)
- 5단계 `predict.py`: 서빙용 예측 함수, ML 예측에 룰 기반 안전장치 덮어씌움
- 6단계 `export_onnx.py`: v2 모델 ONNX 변환
- 실행 순서: 가상환경 활성화 후 `python -m src.<파일명>` 순서대로 실행
- 검증: `python -m tests.scoring_sanity_check` (채점 규칙 회귀 검사),
  `python -m tests.env_profiles_check` (환경 프로파일 검증 로직 검사),
  `python -m tests.teacher_scoring_manual_check` (눈으로 확인)

## 환경 프로파일 (LLM 활용)
3단계에서 쓰는 환경 분포를 LLM으로 생성한다. `src/env_profiles.py`.

**왜**: 기존 균등 샘플링은 근거가 없고 실제 분포와 다르다. 실제로 광량을 선형 균등으로 뽑았을 때
실사용에서 가장 흔한 100~500lux(창에서 떨어진 거실 안쪽)가 전체의 1%밖에 안 잡혀
그 구간 모델 오차가 MAE 2.42까지 올라갔고, 로그 균등으로 바꾸자 0.81로 떨어졌다.
더 근본적인 문제는 축 간 상관이다 — 남향 창가 여름은 광량도 높고 온도도 높은데,
각 축을 독립적으로 균등 샘플링하면 "어둡고 무더운 실내"처럼 실재하지 않는 조합에
학습 데이터가 낭비된다. 프로파일을 먼저 고르고 그 안에서 흔들면 상관이 유지된다
(테스트 기준 실외 광량-온도 상관 0.94, 균등 샘플링은 0에 가깝다).

**LLM 출력을 그대로 쓰지 않는다**: LLM 생성 데이터는 모델 편향 때문에 실제 분포에서
체계적으로 벗어나는 것이 보고되어 있다. 그래서 생성 → 검증 → 사용으로 나누고,
검증(`validate_profiles`)은 LLM 없이 기계적으로 한다 — 물리 범위, 실내 광량 서열
(남향 > 동서향 > 북향 > 무창), 실외 계절 기온 서열, 실내/실외 기온 변동 관계, 계절 커버리지.
검증에 걸린 프로파일은 버린다. 검증 로직 자체가 위반을 잡아내는지는
`tests/env_profiles_check.py`가 확인한다(8가지 위반 유형).

```bash
export ANTHROPIC_API_KEY=...          # 또는 `ant auth login`
python -m src.env_profiles generate   # LLM 호출 -> JSON 저장 (비용 발생, 1회성)
python -m src.env_profiles validate   # 저장된 JSON 검증만 (API 불필요)
```

생성 결과(`data/processed/environment_profiles.json`)는 커밋한다. 그래야 API 키 없이도
파이프라인이 재현되고, 어떤 분포로 학습했는지 감사할 수 있다.
파일이 없으면 3단계는 균등 샘플링으로 자동 폴백하므로 **프로파일 도입 전후를 비교할 수 있다**
(폴백 경로가 베이스라인 역할을 한다).

## 채점 규칙 (3차 데이터 기준)
원예팀이 전달한 '그룹별 가중치' / '그룹별 판정 기준' 시트를 근거로 한다.

- 광량/온도/습도를 각각 4단계로 판정한 뒤 생육형 그룹별 가중치로 가중합
  - ① 거의 문제없음(적정범위) 100점 → ② 생육 둔화 → ③ 생육 정지 0점 → ④ 피해 발생(총점 0점)
- 그룹별 가중치(광량:온도:습도) — 관엽식물 30:40:30 / 다육·선인장류 35:40:25 / 목본류·초본 화훼류 40:40:20
- 총점 0점(④)은 원예팀이 「0점 기준」으로 확정한 두 가지에만 적용: 한계온도 이탈, 재배구분 불일치
- 광량만 절대 lux가 아니라 **적정범위 대비 배율**로 채점 — 종별 요구량이 300~70,000lux로 200배 넘게 차이나기 때문
- **누적 입력 처리**: 감점 채점(광량/온도/습도)은 기간 **평균**, 한계온도 게이트만 기간 **극값**을 쓴다.
  게이트까지 평균으로 판정하면 겨울 한파가 평균에 묻혀, 겨울에 죽을 식물이 "적합"으로 추천된다
  (실측: 6개월 평균 기준 24종, 1년 평균 기준 28종 오추천). 여름처럼 기간 내 변동이 작으면 차이가 없다
- 판정 경계값은 전부 `config.py`의 `SCORE_*` 상수. 원예팀 답변이 오면 **상수만 교체하고 3~6단계를 재실행**하면 된다

### 원예팀 확인 대기 중인 항목 (AI팀 잠정 판단으로 진행 중)
`config.py` 각 상수 주석에 확정/잠정 여부를 표시해뒀다.

| 항목 | 현재 처리 | 확인 요청 내용 |
|---|---|---|
| "③ 생육 정지 / ④ 피해 발생" 병기 구간 | ③(감점)으로 처리 | 두 단계 구분 |
| 광포화점 초과 / 광보상점 미만 | 0점 아닌 감점 | 0점 처리 시 일반 실내·실외에서 추천 0종이 됨 |
| 습도 80% 초과 | 감점, 기준은 `max(80%, 종별 적정 상한)` | 적정 상한이 80% 이상인 9종과 충돌 |
| 적정 광량 vs 광보상점·광포화점 | 종별 적정 광량 우선 | 두 값이 어긋나는 종 88건 (`light_range_conflicts.csv`) |
| 한계온도 상한(41~50℃) | 게이트로만 사용, ② 구간 끝으로는 안 씀 | 생육 한계인지 치사 온도인지 근거 |
| 광보상점·광포화점이 범위 표기 | 넓은 쪽을 경계로 사용 | 단일 임계값 |

## 사용법
- `predict.py`의 `predict_all()` 함수 하나만 호출하면 됨
- 입력: 기간 누적 광량(lux)/온도(℃)/습도(%) 배열 + 실내/실외 여부
- 출력: 식물명 / 학명 / 점수, 내림차순 정렬된 표

```python
import pandas as pd
from src import config
from src.predict import predict_all
from src.teacher_scoring import summarize_environment

plants_df = pd.read_csv(config.NORMALIZED_OUTPUT_PATH)

# 기간 누적 배열을 그대로 넘긴다(리스트/numpy 배열/Series 모두 가능).
env = summarize_environment(
    light=daily_light_values,        # 예: 최근 90일 광량
    temp=daily_temp_values,
    humidity=daily_humidity_values,
    cultivation_context=config.CULTIVATION_INDOOR,  # 또는 CULTIVATION_OUTDOOR
)
result = predict_all(plants_df, env)
```

- `summarize_environment()`는 스칼라도 받는다 — 단일 값을 주면 관측 1개짜리 기간으로 취급한다
- 기간 길이는 게임에서 넘기는 배열 길이를 그대로 따른다. `config.ENV_WINDOW_DAYS`는 학습
  데이터를 만들 때 쓰는 기본 기간(90일)이라, 서빙 기간이 크게 달라지면 재학습이 필요하다

- 점수 계산은 ML 모델(`v2.joblib`) 기반, 생존/재배 불가능 조합은 항상 0점 강제
- 추천 이유 설명이나 "광량 부족" 같은 경고 라벨이 필요하면 → `teacher_scoring.score_plant_detail()` 사용.
  총점과 함께 요인별 점수·게이트 사유를 돌려준다. 가중합 구조상 한 요인이 0점이어도 총점은
  절반 정도까지만 떨어지므로, 총점만으로는 부적합 사유가 드러나지 않는다
- 파이썬이 아닌 환경(게임 엔진 등)에서는 `v2.onnx` 사용

## 현재 상태
- 3차 데이터(100종, 광보상점·광포화점·한계온도 상하한·기후형·생육형그룹 추가) 반영 완료
- 원예팀 판정 기준 기반 4단계 채점 + 그룹별 가중치 적용 완료
- 기간 누적 입력 구조 적용 완료 (감점은 평균, 게이트는 극값)
- LLM 환경 프로파일 생성·검증 모듈 구현 완료. **생성은 아직 실행되지 않았다**(API 키 필요) —
  현재 학습 데이터는 균등 샘플링 폴백 경로로 만들어진 것이다
- 모델 v2 재학습 완료 — 테스트셋 MAE 0.42점
- `tests/scoring_sanity_check.py` 7개 항목 전체 통과

## 참고사항
- **룰과 ML의 차이**: 룰(`teacher_scoring`)은 정확하고 100종 채점에 2.2ms, ML(`predict`)은
  같은 작업에 약 309ms다. ML 모델은 정확도나 속도 때문이 아니라 **ONNX로 non-Python 런타임에
  배포하기 위한 압축본**이다. 파이썬에서 서빙한다면 룰을 직접 쓰는 편이 더 정확하고 빠르다
- **모델 하이퍼파라미터**: 더 깊은 모델(d8/n600, d10/n600)이 테스트 MAE를 0.52 -> 0.25로 절반
  줄이지만, 정작 오차가 큰 극단 구간은 개선되지 않고 ONNX 크기만 1.6MB -> 7.3/13.4MB로 커진다.
  게임 엔진 내장 제약을 고려해 현재 설정(d6/n400)을 유지한다
- **모델 근사 오차가 남는 구간**
  - 학습 분포 밖 입력: 기간 평균이 극단적인 조합(예: 3개월 평균 광량 10만lux)은 현실에
    존재하지 않아 학습 데이터에 없고, 넣으면 오차가 크다. 게임에서 넘기는 값이 기간 평균이
    맞는지 확인 필요
  - 사용자 환경 온도가 어떤 종의 한계온도와 정확히 같은 지점: 룰 자체가 그 점에서 불연속이라
    (미만은 게이트 0점, 이상은 감점 점수) 연속 함수인 회귀모델은 구조적으로 재현할 수 없다.
    다만 게이트는 `predict.py`가 룰로 강제하므로 "추천/제외" 판정 자체는 틀리지 않는다
- 학습 데이터 샘플링 범위(`config.py`의 `SYNTHETIC_*`)는 조사 자료 기반 잠정치인데 근거 문헌이
  남아있지 않다. 기상청 평년값 등 확인 가능한 출처로 교체 필요(`config.py` TODO 참고).
  환경 프로파일을 생성해 쓰면 이 범위는 폴백 경로에서만 쓰이게 된다
- 광량은 로그 균등으로 샘플링한다 — 채점이 로그 스케일이고, 선형 균등으로 뽑으면 실사용에서
  가장 흔한 100~500lux(창에서 떨어진 거실 안쪽)가 전체의 1%밖에 안 잡힌다
- 게이트가 많이 걸리는 시나리오(한겨울 등)에서는 상위 10종이 3점 안에 몰린다. 살아남은 종이
  전부 내한성 종이라 실제로 적합도가 비슷한 것이라 채점 오류는 아니지만, 상위권 순서를
  그대로 노출하면 임의로 보일 수 있다 — UI에서 동점 처리 방식 고려 필요
- 식물 종 100 → 300종 이상 증가 시 모델 성능 재검증 필요
- `models/recommendation_model_v1.*` 는 2차 데이터 + 구버전 채점 규칙으로 학습한 모델이다.
  비교용 기록으로만 남겨두고 서빙에는 쓰지 않는다
